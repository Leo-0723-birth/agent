# Agentic 监管问询扫雷预警系统 —— 框架结构说明与改进方向

> 基于现有代码（`api/`、`backend/`、`docs/ui_preview_主控页.html`）的实测梳理。
> 目的：给你一份可对齐的"现状地图 + 痛点清单"，便于你针对性给出架构/解耦/容错/可扩展/性能的修改建议。
> 技术栈基线：FastAPI + Pydantic v2 + asyncio + LangGraph(可选) + 原生 JS 单文件前端 + WebSocket 进度 + 离线快照。

## 一、整体架构（分层）

```

│ 前端  api/static/index.html  （原生 JS 单文件，2931 行）            │
```

三条主链路：
- **离线链路**：`POST /api/analyze` → `run_pipeline` → `offline_to_response` 读 `backend/data/output/reports/*.json` → 映射成 `AnalyzeResponse`（秒级，不跑模型）。
- **实时链路**：`POST /api/scan{realtime:true}` → 建 `TaskState` → `asyncio.create_task(run_scan_task)` → 抢 `_scan_lock` → `StreamingOrchestrator.run()` 在线程池执行 → 进度经 `asyncio.Queue` 推 WebSocket。
- **兜底链路**：实时任一环节失败/超时 → `_fallback_after_error` 自动回离线快照（有则 `fallback`，无则 `failed/fatal`）。

## 二、核心模块说明

### 1. API 层 `api/main.py`
- 10 个端点 + 1 个 WebSocket + 静态挂载（`api/static`）。
- CORS 全开（`allow_origins=["*"]`，仅开发期可接受）。
- `scan` 端点：`realtime=false` 秒返离线（409 冲突仅实时模式出现）；`realtime=true` 创建任务，冲突返回 `409{ message, task_id, code }` 由前端 `confirm` 后 `force=true` 重发。
- WebSocket 端点：连接后先补发 `state.progress` 历史（断线重连用），结束后保留 30s 给重连窗口。

### 2. 任务调度层 `api/pipeline.py`（最关键、最复杂，1082 行）
核心数据结构与机制：
- `TaskState`：`task_id / code / status / progress[] / result / error / subscribers(set[Queue]) / cancel_event(threading.Event)`。
- `_task_store`（dict）、`_task_handles`（dict）、`_result_cache`（`OrderedDict` LRU=20）。
- `_scan_lock = asyncio.Lock()`：**同一时刻只跑一个实时任务**（串行，避免全局模型/状态竞争）。
- 进度发布：`_thread_safe_emit(loop, state, msg)` → `loop.call_soon_threadsafe(_record_message)` → 写 `state.progress` 并 `put_nowait` 给所有订阅队列（线程安全桥接 executor→事件循环）。
- `run_scan_task`：`async with _scan_lock` 内 `await asyncio.wait_for(asyncio.shield(loop.run_in_executor(None, streamer.run)), timeout=600)`。
- `StreamingOrchestrator`：**在 API 层又实现了一遍 7-Agent 线性编排**（7 个 `_run_*` + `_AGENT_ORDER`），负责在每个 Agent 前后发 `ProgressMessage`，并通过 `_detail_callback` 把 Agent 内部事件翻译成进度。
- 字段映射：`_map_shap_to_factors / _map_financial_table / _map_attribution_* / _map_similar_cases / _map_announcement_risks` 等，把离线报告 JSON 翻译为前端 `AnalyzeResponse`。

### 3. Agent 流水线 `backend/agents/`
- `base.py` `AgentBase`：子类实现 `execute(company, ctx)`，基类 `run()` 自动包 `run_id/耗时/trace`，追加进 `ctx.trace_log`；`_report_progress` 回调向上报进度。
- `orchestrator.py` `SweepingOrchestrator`：
  - 优先用 `graph.build_graph()`（LangGraph 7 节点图）；
  - 若 LangGraph 不可用，回落**确定性串行编排**（`_run_announcement→financial→predict→cases→chunks→attribution→report`）。
  - 同时持有 `use_llm / use_finbert / use_rule / rate_limit / max_documents` 等构造参数。
- `graph.py`：LangGraph `StateGraph(SweepState={ctx,company,window,as_of})`，7 节点；内置**线程看门狗** `_run_with_deadline`（daemon 线程 + `join(timeout)`，超时记 trace 不阻断）；`predictor/chunk` 为容错节点（异常标记 skipped）。可选 `MemorySaver` checkpointer 支持断点续跑。
- 7 个 Agent：公告研读 / 财务异常 / 预测建模（XGBoost+LightGBM+RF 三模型集成 + SHAP，查表推理）/ 案例匹配（BGE+RRF）/ 段落召回 / 归因 / 报告。

### 4. 共享上下文 `backend/context.py`
- `Context` dataclass：主时钟 = `company/window/as_of`；子结构 `Semantic / Financial`；外加 `features/prediction/cases/chunks/attribution/report/trace_log`。
- **Agent 间唯一通信方式**：不直接互相调用，只读写同一 `ctx`。
- 问题：`ctx.use_llm / ctx.use_bge / ctx.max_documents / ctx.cancel_event / ctx.meta` 等字段**未声明在 dataclass 上**，靠鸭子类型动态挂，无类型安全。

### 5. Skills 能力层 `backend/skills/`
- 30+ 模块，职责混合：I/O 类（`crawl_*` 爬 cninfo/舆情/治理）、计算类（`embedding / f2_calc / feature_composer`）、纯函数类（`risk_labels / stock_code`）、存储类（`vector_store / chunk_store / concern_store`）。
- 无统一接口/注册表，Agent 直接 `import` 具体 skill。

### 6. 配置与 LLM
- `config.py`：路径/阈值/模型名集中（单一来源），支持环境变量覆盖。
- `llm.py`：`chat / chat_json / chat_structured` 统一入口；双通道（LangChain `ChatDeepSeek` 优先，requests 直连兜底）；低温度 0.1 + JSON 约束；禁用 DeepSeek thinking（防吃 max_tokens）。

## 三、通信机制（四层）

| 层级 | 机制 | 载体 |
|------|------|------|
| Agent ↔ Agent | 共享可变 `Context` 对象 | `backend/context.py` |
| Agent → Orchestrator | 构造注入 `progress_callback` | `base._report_progress` → dict |
| Orchestrator → API | 线程安全桥接 | `loop.call_soon_threadsafe` → `asyncio.Queue` |
| API → 前端 | HTTP(JSON) + WebSocket | `AnalyzeResponse` / `ProgressMessage` |

- **线程边界**：实时流水线是**同步阻塞**代码，跑在 `run_in_executor` 的默认线程池；但 `_scan_lock` 保证同时只有一个。进度从工作线程 → `call_soon_threadsafe` → 事件循环 → 广播给所有 WS 订阅者。
- **断线重连**：WS 连接即补发 `state.progress` 全量历史；前端 `AppState.messageIds` 去重；`heartbeat` 保活。

## 四、任务调度方式

**双模式**：
- 离线（`realtime=false`）：不建任务、不连 WS，直接读盘映射返回（cached）。
- 实时（`realtime=true`）：建任务 + WS 推送，结束/失败/取消进入终态机 `TERMINAL_STATUSES={completed,failed,fallback,cancelled}`。

**串行锁 + 取消**：
- `_scan_lock` 强制单任务；切换公司时前端先 `DELETE` 旧任务，或 `force=true` 由后端 `cancel_task` 设 `cancel_event`。
- 协作取消：仅在每个 Agent 边界检查 `ctx.cancel_event.is_set()`；已进入某 Agent（如长 LLM/PDF 下载循环）内不检查。

**超时与兜底**：
- `run_scan_task` 外层 `asyncio.wait_for(..., timeout=600)`。
- `graph.py` 节点看门狗（daemon 线程 join 超时）——**但实时路径走 `StreamingOrchestrator`，并非 LangGraph，该看门狗对实时接口实际不生效**。
- 失败 → `_fallback_after_error`：有离线快照则 `fallback`（带 `result`），否则 `failed/fatal`。

## 五、前后端数据连接与页面设计

### 5.1 数据契约（Pydantic ↔ JS）
- 后端 `AnalyzeResponse` 用 camelCase 字段（`factorsList / similarCases / announcementRisks / attributionEvidence / riskFactorDetails / reportMarkdown / traceLog`），与前端 JS 结构严格对齐（写在 `api/models.py` 注释里"与前端对齐"）。
- 实时进度 `ProgressMessage`：`{type, step, total, agent, agent_key, status, progress_percent, message, elapsed_ms, fatal, result, error}`。
- 映射逻辑全在 `pipeline.py` 的 `_map_*` 函数里（后端负责"报告 JSON → 前端结构"），前端**只渲染、不翻译**。

### 5.2 接口清单（前端实际调用）
| 前端调用 | 方法/路径 | 用途 |
|----------|-----------|------|
| `fetchAnalysis` | POST `/api/analyze` | 批量离线分析 |
| `fetchSingleCompany` | GET `/api/company/{code}` | 单公司离线 |
| `startRealtimeScan` | POST `/api/scan` + WS `/ws/pipeline/{id}` + DELETE `/api/scan/{id}` | 实时扫雷 |
| `loadCompanyData(code,false)` | 上述离线 | 兜底回退 |
| `confirmCompanySelection` | `/api/companies`（实际未被前端用） | 公司列表 |

### 5.3 前端状态与渲染
- `AppState`：`currentCompany / currentTaskId / scanStatus / agentStates / agentResults / resultCache(Map) / realtimeMode / subscribers`（手写发布订阅 `subscribe/set`）。
- 渲染：`renderDashboard / renderPipelineSteps / renderTopPipeline / renderAnnouncementRisks / renderSimilarCases / renderAttributionEvidence / renderAudit` 等，**每次消息全量重建对应 DOM 片段**（无虚拟 DOM）。
- 页面结构：欢迎页 → 主控仪表盘（问询概率大数字 + 风险徽章 + 6 Agent 流水线状态条 + 因子卡 + 5 Tab：风险概览/风险证据/比赛历史库/公告清单/审计信息）→ Agent 详情视图。

### 5.4 设计风格
- 原生 JS + 内联 CSS（零构建，适比赛演示），深色金融蓝主题，风险色：低 `#10B981` / 中 `#F59E0B` / 高 `#EF4444`。
- 风险概率**涨=红、跌=绿**符合 A 股惯例（前端用红表示高风险）。

## 六、需要改进的具体方向与痛点（供你给修改建议时对齐）

### A. 架构 / 模块解耦
1. **两套 Orchestrator 职责重叠**：`SweepingOrchestrator`（backend）与 `StreamingOrchestrator`（api/pipeline.py）各自实现一遍 7-Agent 线性编排与 `_run_*` 派发。新增 Agent 要在两处同步改，且跳过逻辑（`chunk` 容错）两处写法不一致。**建议**：API 层只做"任务/进度/WS"，编排逻辑收口到 `backend/agents` 一个 `Orchestrator`；进度回调作为编排器的标准接口透传，API 不再重写 dispatch。
2. **Context 是"上帝对象"且字段漂移**：`use_llm/use_bge/max_documents/cancel_event/meta` 等动态挂到 dataclass 上，无类型、无校验，`to_dict` 经 `asdict` 遇到 `threading.Event` 等非序列化对象会炸。**建议**：把运行期参数与取消信号从 Context 拆出（传参 / 独立 `RunContext`），Context 只承载业务数据，并加 `pydantic` 校验或 freeze。
3. **`_orchestrator_pool` 无界**：按参数组合缓存 `SweepingOrchestrator`（每个含编译图 + 可能加载的模型），无 LRU、无淘汰。**建议**：固定少量配置档 + LRU，或按请求重建轻量编排器（图编译成本可控时）。

### B. 错误处理增强
4. **串行锁 + 不可取消线程 = 队头阻塞**：`asyncio.shield` 包住 `run_in_executor`，超时后底层线程**不会被取消**，仍持有 `_scan_lock` 直到跑完（公告+LLM 最坏 ~1320s）。一个挂死任务会阻塞后续所有实时请求最长 10+ 分钟。**建议**：实时路径也启用 `graph.py` 的节点看门狗（或在 `StreamingOrchestrator` 内加 per-agent 超时/取消点），超时即释放锁并标记 skipped/timeout，而不是依赖 shield。
5. **LangGraph 看门狗是实时路径的"死代码"**：实时接口走 `StreamingOrchestrator` 而非 `graph.build_graph`，`graph.py` 的 `_run_with_deadline` 对真实接口不生效。**建议**：统一一条实时执行路径（要么都走 LangGraph，要么都把看门狗搬到 StreamingOrchestrator）。
6. **取消只到 Agent 边界**：长 LLM 调用 / PDF 批量下载循环内不检查 `cancel_event`，无法中途中断。**建议**：在 I/O 密集循环（PDF 下载、批量 LLM）内插入 `cancel_event` 轮询与超时。
7. **离线映射对畸形报告脆弱**：`_map_*` 假设报告结构完整，缺字段会 `KeyError` 冒泡成 500；`get_offline_result` 的 except 未覆盖全部 `_map_*` 异常。**建议**：`_map_*` 全部加 `dict.get` 防御 + 单报告映射失败不影响其他字段/公司，并加 schema 校验。

### C. 可扩展性提升
8. **加一个 Agent 要改 5 处**：orchestrator(LangGraph+兜底) + StreamingOrchestrator(`_run_*`+`_AGENT_ORDER`) + graph + 前端 `AGENT_ORDER` + `ProgressMessage` 映射。**建议**：Agent 自描述（声明 `name/key/display/order/skip_on_error`），编排器与前端从注册表自动发现；`_AGENT_ORDER` 与后端 `_AGENT_ORDER` 应同源。
9. **运行期开关靠构造参数逐层透传**：`use_llm/use_finbert/use_rule/rate_limit/max_documents` 在每个 Agent `__init__` 签名里穿来穿去。**建议**：收口为一个 `RunConfig` dataclass，Agent 从 ctx/RunConfig 读，避免签名膨胀。
10. **Skills 无统一接口/注册表**：30+ 模块混合 I/O、计算、纯函数，Agent 硬 import。**建议**：按"数据源 / 计算 / 存储"分三层，定义 `Skill` 协议（如 `run(ctx, config) -> None`），便于替换与测试。
11. **Predictor 仅"查表 CSV"模式**：新增在线特征推理后端需同时改 predictor + feature_loader，不插件化。**建议**：推理后端抽象为 `PredictorBackend` 接口（lookup / online / survival），编排器按配置选择。

### D. 性能
12. **实时严格串行**：`_scan_lock` 单任务，评审判多公司只能排队；且 `run_in_executor` 默认线程池被锁废掉并发。**建议**：若评测允许，按"公司级"并发（每公司独立特征/模型推理可并行，仅共享 LLM 客户端需池化）；或提供"批量预计算离线报告"一键生成，演示直接走离线秒出。
13. **离线读盘无预热/无清单缓存**：每次 `offline_to_response` 重读 `manifest.json` + 报告 JSON + markdown；`_result_cache` 仅 20 且冷启动为空，首访慢。**建议**：manifest 启动时加载一次（或带 mtime 失效），报告 JSON 进缓存，健康/启动接口可预热热门公司。
14. **前端无虚拟 DOM、每次消息全量重渲**：实时进度高频推送时反复 `renderDashboard` 重建 DOM。**建议**：进度类更新只 patch 状态条/数字（增量 diff），仅 `complete` 时整页渲染；因子卡/证据表用文档片段增量追加。
15. **BGE 加载阻塞**：`EMBEDDING_BACKEND=bge` 首次加载 ~1.3GB 权重会卡住首请求；fallback(65536 维) 与案例库不兼容仅是占位。**建议**：embedding 模型独立懒加载 + 预热；或默认走离线已算好的向量，实时仅做轻量检索。

### E. 前后端契约一致性（易踩坑）
16. **后端 7 Agent vs 前端 6 Agent 显示不一致**：后端发 `chunk` 进度（`agent_key=chunk`），前端 `AGENT_ORDER` 无 chunk，`updateAgentState` 查不到 → 静默丢消息；顶部步骤条 `mapStepToTopPipeline` 把 step 5/6 都映射到第 5 格。**建议**：前后端 Agent 清单同源（见第 8 点），`chunk` 要么进前端展示，要么在后端标 `substep` 不单独占 step。
17. **`_map_*` 的人读名称表重复两份**：`_map_shap_to_factors` 与 `_map_risk_factor_details` 各维护一套 `name_map/tag_map/desc_map`，改一处易漏。**建议**：抽成 `backend/mapping/display_names.py` 单一来源。
18. **`_map_attribution_evidence` 归因匹配脆弱**：按 `taxonomy_l2→l1→risk_factors[0]` 兜底，可能把证据错配到不相关因子。**建议**：在 `attribution` 阶段就产出"因子→证据 id"的显式引用（已有 `evidence_citations` 优先路径，但未覆盖全部场景），减少前端猜测。
19. **`DEMO_COMPANIES` 硬编码 3 家，忽略 `/api/companies`**：前端只给 3 个快捷按钮 + 从 `resultCache` 选；`/api/companies` 返回全部离线公司但未被消费。**建议**：前端公司选择器直接消费 `/api/companies`，展示全部可用离线报告，去掉硬编码。

### F. 其他
20. **README 与代码漂移**：README 目录树写有 `ui/`（旧 Streamlit）但实际不存在；声称"7-Agent"但前端显示 6；`config.py` 与 `llm.py` 各加载一次 `.env`（双加载）。**建议**：README 以代码为准更新；`.env` 加载统一收口到 `config.py`。

## 七、给定修改建议时的"一致性约束"（请保持）

- 后端继续：**FastAPI + Pydantic v2 + asyncio + 原生 dataclass Context + 可选 LangGraph**，不要引入新重型框架（如 Celery/Dramatiq）除非为并发调度必需。
- 前端继续：**单文件原生 JS / 内联 CSS、零构建**，改动以"增量 patch + 同源 Agent 注册表"为主，不要引入 React/Vue 构建链（违背比赛零依赖演示初衷）。
- 通信继续：**Context 作为 Agent 唯一载体 + 进度回调 + WebSocket 进度**，不要改成消息队列/事件总线（过度设计）。
- 容错继续：**优雅降级 + 离线兜底**哲学，新 Agent 默认 `skip_on_error` 不打断流水线。
- 配置继续：`backend/config.py` 单一来源 + 环境变量覆盖。

## 八、补充审查（模型复查 · 新增痛点 21–32）

> 换模型后二次重审，聚焦上次未覆盖的"运行期行为、安全与可观测性"深层问题。

### G. 并发与事件循环（本次最重要）
21. **离线路径是"假 async"，阻塞事件循环**：`run_pipeline`/`get_company`/`list_available_companies` 声明为 `async def`，但内部是纯同步读盘（`_load_manifest` 全量解析 manifest.json + 逐份 `json.loads` 报告）+ 一串 `_map_*`，**没有任何 `await`**。离线查询期间会卡住整个事件循环——WebSocket 心跳、实时任务的进度推送、其他请求全部停摆。**建议**：离线读盘改 `run_in_executor` 放线程池；或 manifest/报告加内存缓存（mtime 失效）；或干脆改成 `def`（FastAPI 对普通 `def` 自动走线程池），让 async 只留给真正的 I/O。
22. **`_task_store` 永不清理（内存泄漏）**：`create_task` 写入后全程无 `pop/del`；`state.progress`（累积全部消息）+ `state.result`（整份报告）永久驻留内存。演示期反复扫雷、`force` 频繁切换公司，内存会单调上涨。**建议**：终态任务做 TTL 或"保留最近 N 个"的清理；`force` 切换时顺手清理旧 task。

### H. 安全
23. **前端 XSS 面偏大**：39 处 `innerHTML`，`escapeHtml` 仅 5 处调用。`summary`（后端注入 `<b>`）、`conclusion`、`reportMarkdown`、`attribution` 等直接 innerHTML；`evidence`（爬取的公告原文/股吧舆情，属外部数据）在部分渲染路径未转义。**建议**：所有"外部原文"统一 `escapeHtml`，仅后端可信生成的 summary HTML 走白名单；或改 `textContent` + 受控富文本节点。
24. **无鉴权**：CORS 全开 + `/ws/pipeline/{task_id}` 无 token，task_id 是 12 位 hex 可枚举；任何人可连 WS 看进度/触发取消。**建议**：轻量加 `X-API-Key` 或来源校验（演示可简化，但需意识到暴露面）。
25. **密钥与路径配置散落**：`llm.py` 手写解析 `.env`（只 3 个 `DEEPSEEK_*`），`config.py` 用 `load_dotenv` 加载全量，双入口易不一致；`config.py` 硬编码 `D:\BaiduNetdiskDownload`、`D:\新建文件夹` 等绝对 Windows 路径。**建议**：env 加载收口一处；绝对路径全部抽到 `.env`/配置映射，保证跨机器与 CI 可移植。

### I. 一致性 / 健壮性
26. **`agents/__init__.py` 的 `__all__` 缺 `ChunkRetrieverAgent`**：懒加载表 `_LAZY_EXPORTS` 有它，但 `__all__` 没列，`from backend.agents import *` 会漏掉。**建议**：`__all__` 与 `_LAZY_EXPORTS` 同源生成。
27. **模型/数据集在 orchestrator pool 下重复加载**：每个 `SweepingOrchestrator`（`_orchestrator_pool` 按参数组合缓存）各自实例化 `PredictorAgent` → 各自 `_load_df`（读全量 CSV）+ 9 个模型（每个数 MB）。参数组合一多内存成倍。**建议**：模型/数据集做成进程级单例（模块级缓存），orchestrator 只持有轻量编排；pool 加 LRU。
28. **测试覆盖严重不均衡**：`backend/tests` 12 个单测，但 `api/tests` 仅 1 个 `test_backend_runtime.py`（5KB），任务调度、WS 推送、取消、兜底、409 冲突、缓存这些**核心并发逻辑几乎零测试**。**建议**：用 pytest-asyncio 补 `pipeline` 的并发/取消/兜底/缓存单测 + `_map_*` 契约金样。

### J. 可观测性
29. **日志用 `print`（56 处）**：散布 `llm.py`/`orchestrator.py` 等，无结构化、无级别、无 run_id/task_id 关联，排障靠翻 stdout。**建议**：标准库 `logging` 统一 logger，关联 `run_id/task_id`，生产可接文件/告警。
30. **trace_log 只进内存/前端审计 Tab**：实时路径的 trace 不落盘、无检索，赛后复盘审计缺据。**建议**：按 `task_id/company` 落盘 JSONL（复用 `TraceLogger`），或接轻量 SQLite。

### K. 可扩展深化
31. **`window` 参数半链路失效**：`ScanRequest.window` 一路传到底，但离线 `offline_to_response` 固定映射 60d（`probability_60d`），`_cache_key` 虽含 window 却只有一套 60d 报告——前端 predictor 详情页有 30/60/90 切换按钮，主数据却不变。**建议**：明确 window 语义（离线是否支持多窗口），或从报告一次性下发 30/60/90 三档概率。
32. **`as_of` 不可控**：实时链路 `as_of or str(date.today())` 固定"今天"，接口未暴露，无法做"回到历史时点"的回测/复现演示。**建议**：`ScanRequest` 暴露可选 `as_of`，供演示复现。
