# 竞赛演示操作手册

> 适用版本：2026-08-29 之后的主分支（满配三通道 + F1 实时上游 + 50/100/150 份抽取）
> 演示前通读一遍，按"演示前一天"和"演示当天"两个清单执行。

---

## 一、演示前一天：预热（一次性，约 30-40 分钟）

实时扫雷的性能瓶颈集中在**第一次**对某公司做 F1 语义上游计算（CPU 交叉编码 20-40 分钟/50 份）。
所有中间产物都有持久缓存，预热后当天演示就是分钟级。

1. **关闭大内存应用**：微信、豆包、多余浏览器标签、不用的 VS Code 窗口。
   机器只有 8GB 内存，F1 上游子进程需要 ~2.5GB 提交内存；不足时报
   `os error 1455（页面文件太小）`，语义特征会降级为填 0（功能不崩，但演示效果打折）。

2. **启动服务并预热目标公司缓存**（对演示要用的每家公司各跑一次）：

   ```bat
   start_api_verify.bat
   ```

   然后在页面发起实时扫雷：公告份数选 **50**、LLM 精细抽取**开**。
   首次会下载/解析/嵌入/rerank 全量计算（20-40 分钟），完成后即预热完毕。

3. **确认预热成功**（两个标志）：
   - `GET /api/health` 返回 `"f1_same_pipeline": "enabled"`（三模型已配置）；
   - 报告 JSON 里 `semantic.data_quality.f1_model_feature_status.upstream.status == "generated"`。

4. 预热产物位置（勿删）：
   - PDF 正文与解析缓存：`backend/data/cache/pdfs/`
   - F1 向量/rerank/情绪缓存：`backend/data/cache/f1_*.json`

---

## 二、演示当天：启动与自检（约 5 分钟）

1. 关掉所有残留 API 进程（**旧实例会占端口、占内存、跑旧代码**）：

   ```bat
   netstat -ano | findstr :8000
   taskkill /PID <上一步的PID> /F
   ```

2. `start_api_verify.bat` 启动（脚本自带 OMP=2 稳定配置，勿改）。

3. 30 秒自检清单：
   - `http://127.0.0.1:8000/api/health`：`realtime_ready=true`、`f1_same_pipeline=enabled`
   - 页面右上角 Agent 就绪绿灯
   - 参数区默认值：公告研读上限=50 份、LLM 精细抽取=开、BGE=开

## 三、演示中：参数选择与预期耗时

| 场景 | 公告份数 | LLM 抽取 | 预期耗时 | 说明 |
|---|---|---|---|---|
| 快速演示 | 50 | 开 | 3-6 分钟（缓存热） | 推荐默认 |
| 完整演示 | 50 | 开 + 讲解报告第六章 | 同上 | 解读章节是亮点 |
| 深度演示 | 100/150 | 开 | 首算可能 30-60 分钟 | 仅当缓存已预热该公司的对应公告 |

界面口径（演示时主动讲）：
- 主控总览与公告研读详情页都显示「近一年 N 份公告，本次按时间最近获取 M 份 PDF（深读 K 份）」；
- 进度条逐份显示「正在下载/解析第 i/N 份」「LLM 精细抽取第 i/N 份」；
- 报告第六章「公告风险原文解读」是 LLM 基于**已核验证据原文**生成的，证据不足处会明确标注。

## 四、常见问题与话术

| 现象 | 原因 | 处理/话术 |
|---|---|---|
| 公告研读 0 条风险信号 | 设计如此：规则候选必须经 LLM 原文校验或双确认才展示（防误报） | "我们只展示经核验的事实证据，候选全部留档可审计" |
| F1 上游 failed / produced_dimensions: 0 | 内存不足（os error 1455）或该缓存未预热 | 关内存占用大户后重扫；缓存后秒级 |
| 任务总超时 | 首算未预热 + 份数大 | 先按 50 份预热，或减份数重试 |
| 风险分数与离线快照不一致 | 实时 vs 离线口径不同，实时为准 | 数据源标识 `dataSource: realtime` |
| 服务端段错误/进程消失 | 8GB 内存被桌面应用挤占 | 关应用重启服务；旧实例务必关闭 |

## 五、答辩要点（技术口径）

1. **三通道抽取与发布策略**：规则词典（高召回候选）→ FinBERT 门控 → LLM 逐字校验；
   只有「LLM 校验通过」或「规则+LLM 双确认」的证据才对外展示，候选全部留档
   （`risk_factor_candidates`），可审计、可解释。
2. **F1 训练同口径实时链路**：600/100 切块 → BGE-large-zh-v1.5(CLS) → 45 风险主题召回 →
   bge-reranker-v2-m3 精排 → finbert-tone 门控打分 → 208 维聚合 → 冻结 PCA50
   （SHA256 校验，revision 与训练清单逐字一致）；模型缺失/失败时明确降级填 0 并审计，
   绝不伪装。
3. **可观测性**：每次扫雷有分步耗时日志（元数据/PDF/规则/FinBERT/LLM）、
   模型版本哈希（manifest-sha256）、F1 同口径审计字段。
4. **工程稳定性**：F1 三模型子进程隔离（崩溃不伤主服务）、多级持久缓存、
   看门狗与总超时随负载自适应。

## 六、已知限制（如实告知评委）

- 公告语义特征首算耗时较长（CPU），已用缓存缓解；生产部署建议 GPU。
- FinBERT 门控阈值 0.5 未经公告标注集校准（代码内有警示标注）。
- 案例库为历史问询函底库，静态合理，不与实时公告联动。
- 缺失 F1 语义特征时按 0 填充（竞赛演示模式），并在响应元数据中留痕。
