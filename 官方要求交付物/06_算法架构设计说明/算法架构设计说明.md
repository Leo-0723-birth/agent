# 算法架构设计说明

## 1. 总体架构

系统采用“数据层—模型层—Agent 层—交付层”四层结构。数据层提供公告、财务、市场、舆情、治理和问询历史；模型层完成 F1-F6 特征构建和 30/60/90 天集成预测；Agent 层通过 LangGraph 编排七个节点；交付层提供 Streamlit、API、批量结果和 Markdown/JSON 报告。

## 2. Agent 链路

`AnnouncementReader → FinancialDetector → Predictor → CaseRetriever → ChunkRetriever → Attributor → Reporter`

所有节点共享 `backend.context.Context`，每个 Agent 只读写自己的字段。`AgentBase.run()` 自动记录 run_id、时间戳、耗时、状态和输出摘要；因此单次请求可以完整回放。

一次 `000004.SZ`、60 天请求会在同一个 Context 中形成公告风险要素、F2-F6 特征、三模型概率、SHAP 贡献、Top-5 案例、chunk 证据、归因叙事和八章报告，同时输出页面对象、JSON API、Markdown 报告和逐节点 trace。

## 3. 核心算法

- 预测：RandomForest、LightGBM、XGBoost 三模型加权集成，分别输出 30/60/90 天概率和 SHAP 特征贡献。
- 语义：官方风险词典、FinBERT（可选）和 LLM（可选）多通道抽取，证据片段保留原文。
- 案例：4785 份历史问询函，标签检索与 BGE 语义检索通过 RRF 融合，返回 Top-5。
- 归因：SHAP 与规则降级归因统一为风险因素，绑定 evidence_id；`validate_narrative` 防止引用证据池外内容。
- 报告：结构化 JSON 与 Markdown 八章报告同步生成并自动归档。

## 4. 稳定性与边界

LangGraph 节点设置超时；预测和 chunk 节点容错降级；离线公告快照可在无网络时运行。所有报告注明数据截止日、来源和免责声明。

公告源访问失败时保留来源和失败原因；FinBERT/LLM 未启用时使用规则通道；BGE 不可用时使用标签检索；预测或 chunk 异常时写 skipped trace 并继续报告生成。结果缺失与低风险明确区分，空值不会被误读为安全信号。
